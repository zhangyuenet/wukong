# Wukong 整体计划 (Project Plan)

本文档规划 Wukong 项目的整体路线。它是一份会持续修订的工作文档，每完成一个
阶段后回来更新。

## 1. 目标

**长期目标**：一个可以用自然语言下达任务的无人机自主工作平台，同一套软件能
适配不同的生活和工作场景。

**第一个场景**：检查房屋的屋檐水槽（gutter）。用户说一句话，无人机起飞、找到
房屋、沿屋檐逐段检查、判断哪里需要清理、把照片交给用户，然后返航降落。

**个人目标**：以这个场景为牵引，系统地积累机器人软件的基础能力，包括感知、
定位、规划、安全，以及机载实时系统与大模型之间的分工。

## 2. 范围

第一个场景要做的：

- 自然语言指令到任务步骤的转换
- 房屋、屋檐、水槽的视觉识别
- 沿屋檐的自主飞行与拍摄
- 水槽状况的图像判断与结果汇报
- 自动返航、降落，以及异常情况下的安全处置

第一个场景不做的：

- 对任意陌生房屋的可靠全自主（真机阶段先限定在已知房屋）
- 贴近障碍物的近距离飞行（保持在屋檐上方和外侧，用高分辨率相机拍摄）
- 任何接触或操作物体的动作
- 超视距飞行

## 3. 设计原则

1. **仿真优先**：每个功能先在仿真中跑通，再考虑真机。
2. **安全靠几何，不靠识别**：避障依赖深度测量，不依赖"认出"障碍物是什么，
   并且在断网时也必须有效。
3. **大模型不阻塞**：语言理解和图像判断不进入任何实时环路。云端变慢或失联时，
   无人机悬停或返航。
4. **先闭环，再变强**：先用最简单的实现打通整条链路，再逐个环节替换成更好的
   实现。
5. **默认保护隐私**：真实的坐标、飞行日志、影像和密钥不进入仓库。

## 4. 系统架构

```
用户的一句话
     │
     ▼
任务规划（大模型，云端）      把指令拆成技能调用序列
     │
     ▼
任务管理（ROS 2，机载）       状态机、进度、电量、异常处置
     │
     ├── 感知（ROS 2，机载）  房屋与屋檐识别、深度测距、视觉定位
     ├── 规划（ROS 2，机载）  沿屋檐的航线、避障
     └── 图像判断（大模型）   每段水槽是否需要清理（异步，不阻塞飞行）
     │
     ▼
飞行控制（PX4）               位置与姿态控制、失效保护、返航
```

各层的时间尺度：

| 层 | 频率 | 位置 |
|---|---|---|
| 姿态与电机控制 | 几百 Hz 以上 | PX4 飞控 |
| 避障、定位、屋檐跟踪 | 10–50 Hz | 机载电脑 |
| 语义决策 | 约 1 Hz 或更低 | 机载或云端 |
| 指令解析、照片判断 | 一次性或异步 | 云端 |

## 5. 技术选型

| 项 | 选择 | 说明 |
|---|---|---|
| 飞控 | PX4 | 与 ROS 2 集成最紧，BSD 许可 |
| 中间件 | ROS 2 | 版本在 M0 阶段按 PX4 文档的推荐确定 |
| 仿真 | Gazebo | 使用 PX4 自带的 X500 四旋翼模型 |
| 开发环境 | Ubuntu（ARM64 虚拟机） | 在 MacBook Air M2（24GB）上用 VMware Fusion 运行，与日后的机载电脑同为 ARM64 架构 |
| 许可证 | Apache-2.0 | 与 ROS 2（Apache-2.0）和 PX4（BSD-3）兼容，带专利授权条款 |
| 大模型 | 云端 API | 先用现成的视觉语言模型，后期评估机载小模型 |
| 真机（M4 起） | Holybro X500 v2 + 机载电脑 + 深度相机 | 具体型号在 M4 阶段确定 |

## 6. 里程碑

每个阶段都有明确的完成标准，达到后才进入下一阶段。

### M0 开发环境

- [x] 搭好 Ubuntu 开发环境（步骤见 [DEV_SETUP.md](DEV_SETUP.md)）
- [x] PX4 仿真、Gazebo、ROS 2 三者连通
- [x] 用 ROS 2 节点让仿真无人机起飞、飞到指定点、降落（`wukong_flight` 包的
  `fly_mission` 节点）
- [x] 确定仓库的目录结构和代码规范（见 [CONVENTIONS.md](CONVENTIONS.md)）

**完成标准**：一条命令启动仿真，一个 ROS 2 节点能控制无人机完成起降。

### M1 最小闭环（仿真）

- [x] 输入一句自然语言，大模型把它转换成技能调用序列（`wukong_mission` 的
  `run_task`）
- [x] 技能库的第一版：起飞、飞到某点（可指定朝向）、悬停、拍照、返航、降落，
  以及飞行前的几何检查（`wukong_flight`）
- [x] 无人机飞到房屋旁拍照（仿真房屋世界、相机桥接），照片交给视觉语言模型判断
- [x] 返回一段文字结论（`report.md`）

**完成标准**：在仿真中，从一句话到返航降落全程无人工干预，并得到判断结果。
**已完成（2026-11-20）**：“检查水槽”和“检查屋顶”两条指令在仿真中全程无人工
干预，报告正确指出南侧水槽有落叶。

### M2 完整场景（仿真）

- 在 Gazebo 中搭建带屋檐水槽的房屋，水槽有干净和堵塞两种状态
- 识别房屋并提取屋檐线
- 沿屋檐飞行，逐段拍摄
- 汇总成报告：哪几段需要清理，附对应照片

**完成标准**：对仿真中不同的房屋和水槽状态，报告结果与实际设置一致。

### M3 感知与安全（仿真）

- 用深度相机实现避障
- 加入视觉定位，降低对 GPS 的依赖
- 完整的异常处置：电量不足、云端失联、定位丢失、遇到障碍无法绕行
- 在仿真中加入风和传感器噪声

**完成标准**：在仿真中注入上述每一种异常，无人机都能安全悬停或返航。

### M4 真机准备

- 考取加拿大基础操作飞行员证书，完成无人机注册
- 确定并采购硬件，完成组装
- 台架测试：飞控与机载电脑通信、相机、遥控接管
- 手动试飞，再试最简单的自主起降

**完成标准**：真机能在开阔场地稳定完成自主起飞、悬停、返航，遥控接管可靠。

### M5 真机场景（已知房屋）

- 预先采集一栋已知房屋的屋檐轨迹
- 按轨迹自主飞行、拍摄、判断、汇报
- 全程有安全员随时准备接管
- 记录仿真与真机之间的差异，回头改进仿真

**完成标准**：在好天气下，对已知房屋连续多次完成完整任务，无需人工接管。

### M6 扩展

- 减少对预先采集轨迹的依赖，尝试现场识别和规划
- 评估把部分模型搬到机载运行
- 探索第二个场景，验证平台的通用性

## 7. 节奏

业余时间推进，粗略估计 M0 到 M3 的仿真阶段需要两到三个月，这个数字会在 M0
结束后根据实际进度修正。M4 的考证和硬件采购可以与 M2、M3 并行。

## 9. 主要风险

| 风险 | 应对 |
|---|---|
| Mac 虚拟机跑带相机的仿真太慢 | 控制类开发留在 Mac，视觉仿真到时再评估云端 GPU 或带独立显卡的电脑 |
| 靠近房屋时 GPS 不可靠 | M3 加入视觉定位，并保持与建筑的距离 |
| 电线、细树枝等难以探测的障碍 | 飞行高度和距离留足余量，真机阶段限定在已勘察过的房屋 |
| 住宅区内与旁人的距离不满足基础证书要求 | 试飞前核对法规和空域，必要时考取高级证书或更换场地 |
| 仿真与真机差异大 | M5 中持续记录差异并回头修正仿真 |
| 隐私信息误提交到公开仓库 | 见下一节 |

## 10. 仓库与隐私约定

这是公开仓库，以下内容一律不提交：

- API 密钥和任何凭据（放在 `.env`，参考 `.env.example`）
- 真实的经纬度、航线和围栏文件
- 真机的飞行日志和参数导出
- 实拍的照片、视频和传感器录制数据
- 真实地点的地图和三维重建

拿不准的文件放进 `private/` 目录，该目录已被忽略。需要示例数据时，使用仿真
生成的数据。

计划中的目录结构：

```
wukong/
├── docs/          文档
├── src/           ROS 2 功能包
├── sim/           仿真世界和模型
├── config/        配置（真实环境的配置放 config/local/，不提交）
├── scripts/       环境搭建和启动脚本
└── private/       本地私有文件，不提交
```

引入第三方库前先确认其许可证。GPL 类许可证的库会约束与之链接的代码，需要单独评估。
