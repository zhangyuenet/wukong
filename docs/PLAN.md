# Wukong 整体计划 (Project Plan)

本文档规划 Wukong 项目的整体路线。它是一份会持续修订的工作文档，每完成一个
阶段后回来更新。

## 1. 目标

**长期目标**：一个可以用自然语言下达任务的无人机自主工作平台，同一套软件能
适配不同的生活和工作场景。

**第一个场景**：检查房屋的屋檐水槽（gutter）。用户说一句话，无人机起飞、找到
房屋、沿屋檐逐段检查、判断哪里需要清理、把照片交给用户，然后返航降落。

**房屋检查的目标**：水槽只是第一个用例。用户要求检查的、从房屋外面用眼睛能
分辨的任何东西，都应该能检查：屋顶的烟囱、墙上的窗户、大门、连接前后门的
平台（deck）、台阶等等。见 M5。

**个人目标**：以这个场景为牵引，系统地积累机器人软件的基础能力，包括感知、
定位、规划、安全，以及机载实时系统与大模型之间的分工。

## 2. 范围

第一个场景要做的：

- 自然语言指令到任务步骤的转换
- 房屋、屋檐、水槽的视觉识别
- 沿屋檐的自主飞行与拍摄
- 水槽状况的图像判断与结果汇报
- 自动返航、降落，以及异常情况下的安全处置

第一个场景不做的：

- 对任意陌生房屋的可靠全自主（真机阶段先限定在已知房屋）
- 贴近障碍物的近距离飞行（保持在屋檐上方和外侧，用高分辨率相机拍摄）
- 任何接触或操作物体的动作
- 超视距飞行

## 3. 设计原则

1. **仿真优先**：每个功能先在仿真中跑通，再考虑真机。
2. **安全靠几何，不靠识别**：避障依赖深度测量，不依赖"认出"障碍物是什么，
   并且在断网时也必须有效。
3. **大模型不阻塞**：语言理解和图像判断不进入任何实时环路。云端变慢或失联时，
   无人机悬停或返航。
4. **先闭环，再变强**：先用最简单的实现打通整条链路，再逐个环节替换成更好的
   实现。
5. **默认保护隐私**：真实的坐标、飞行日志、影像和密钥不进入仓库。

## 4. 系统架构

```
用户的一句话
     │
     ▼
任务规划（大模型，云端）      把指令拆成技能调用序列
     │
     ▼
任务管理（ROS 2，机载）       状态机、进度、电量、异常处置
     │
     ├── 感知（ROS 2，机载）  房屋与屋檐识别、深度测距、视觉定位
     ├── 规划（ROS 2，机载）  沿屋檐的航线、避障
     └── 图像判断（大模型）   每段水槽是否需要清理（异步，不阻塞飞行）
     │
     ▼
飞行控制（PX4）               位置与姿态控制、失效保护、返航
```

各层的时间尺度：

| 层 | 频率 | 位置 |
|---|---|---|
| 姿态与电机控制 | 几百 Hz 以上 | PX4 飞控 |
| 避障、定位、屋檐跟踪 | 10–50 Hz | 机载电脑 |
| 语义决策 | 约 1 Hz 或更低 | 机载或云端 |
| 指令解析、照片判断 | 一次性或异步 | 云端 |

## 5. 技术选型

| 项 | 选择 | 说明 |
|---|---|---|
| 飞控 | PX4 | 与 ROS 2 集成最紧，BSD 许可 |
| 中间件 | ROS 2 | 版本在 M0 阶段按 PX4 文档的推荐确定 |
| 仿真 | Gazebo | 使用 PX4 自带的 X500 四旋翼模型 |
| 开发环境 | Ubuntu（ARM64 虚拟机） | 在 MacBook Air M2（24GB）上用 VMware Fusion 运行，与日后的机载电脑同为 ARM64 架构 |
| 许可证 | Apache-2.0 | 与 ROS 2（Apache-2.0）和 PX4（BSD-3）兼容，带专利授权条款 |
| 大模型 | 云端 API | 先用现成的视觉语言模型，后期评估机载小模型 |
| 真机（M6 起） | Holybro X500 v2 + 机载电脑 + 深度相机 | 具体型号在 M6 阶段确定 |

### M3 复杂房屋（仿真）

北美常见的房屋比 M2 的单层长方形房屋复杂得多：独立屋通常地上两层，每层都可能有
若干段水槽，还有车库、门廊等较低的屋顶；联排房屋两户到六户甚至更多连成一排，
共用山墙，只能检查其中一户的范围，而端户的水槽可能有三面。

- [x] 在场景生成器中加入两层独立屋（含较低的车库、门廊屋顶）和多户联排
  （`sim/buildings.py`，屋顶用网格文件）
- [x] 找出离起飞点最近的房屋：先在起飞点上方环视扫描，取最近的建筑
- [x] 从点云中识别多个高度的屋面和屋檐（高度图，`wukong_perception/heightmap.py`）
- [x] 分层扫描：逐站规划，先高圈后低圈；没看到的建筑部分按允许的最高建筑高度禁飞
- [x] 联排中只检查目标那一户：Claude 看一张画了刻度尺的正面照片，判断房屋类型、
  户数和目标户的分界（`classify.py`）；真机阶段由用户确认一次，写入本地场地配置
  （尚未实现确认流程）
- [x] 报告按楼层和方向列出各段水槽

**完成标准**：在单层、两层、联排中间户和联排端户的仿真场景中，无人机只检查目标
房屋，不漏掉它的任何一段水槽（包括端户侧面和较低的屋顶），报告结果与实际设置一致。

**已完成（2026-11-21）**：Gazebo 中由 Claude 判断房屋类型和照片，`two_storey`
24/24、`row_end` 11/11、`row_middle` 8/8，均无漏拍。

**复查（2026-11-22）**：去掉联排场景地图里残留的“这是联排”提示后复测，发现并修复了
几个问题：
- 拍照阶段规划航线时把没看到的空间当成了空地，绕过联排两端时贴着墙飞；
  现在没看到的空间同样是障碍，航线从屋顶上方越过。离线检查（`sim/mission_check.py`）
  新增了航线与真实房屋网格的距离检查（不小于 1 米）。
- 飞行中规划用飞机的实际位置，检查用目标点，航线贴着余量时会被否决；现在都用目标点。
- 短暂收不到 PX4 消息时，状态机把默认值当成了“已落地”而提前结束；现在中断 1 秒内
  保持，超过 1 秒原地降落并持续重发降落指令，直到确认落地。
- 评估（`sim/evaluate.py`）现在还要求每条目标水槽至少 80% 被拍到、飞行完整结束；
  没拍到的段在报告里标为“未检查”。

用新标准复测：两个联排场景都完整飞完、全部覆盖、没有贴墙，`row_middle` 5/6、
`row_end` 12/13，错的两段见下面前两条遗留问题。

遗留问题：
- GPS 漂移让各次扫描之间错开 0.2–0.9 米，偶尔多识别或漏识别一条短屋檐，或者把转角
  推出去约 1 米（例如四坡顶转角处多出一条斜的“东北角水槽”）；扫描配准
  （`register.py`）在真实数据上反而更差，暂未启用。M4 的视觉定位会改善。
- Claude 在刻度尺上读户界的误差有时超过 1.5 米，会把邻居家的一段水槽（连同上面的
  杂物）算进目标户。可以在低圈靠近共用墙时再拍一张近照细读，或者由用户确认。
- 相机向下只能看 29°，飞机下方和近处地面是盲区；目前只把建筑范围内（联排沿长轴
  再延伸 15 米）没看到的空间当作障碍，其余未知空间留给 M4 的避障。
- 真机上需要用户确认房屋类型和户界的流程。

### M4 感知与安全（仿真）

- 加入视觉定位，降低对 GPS 的依赖
- 完整的异常处置：电量不足、云端失联、定位丢失、遇到障碍无法绕行

### M5 通用检查（仿真）

M2、M3 只会检查水槽：大模型只负责读懂指令、判断照片，中间“去哪里拍”完全靠
几何程序从高度图里找屋檐。屋檐是房屋轮廓上的几何边，深度相机能直接找到；窗户、
大门、台阶、烟囱上的裂缝这类东西，几何上找不出来，或者根本不知道该找什么。
M5 把“找什么、在哪里”交给大模型和照片，把“怎么安全地飞过去拍”留给程序：

```
指令 → 理解检查对象 → 扫描房屋（M3 已有）→ 取样拍照 → 大模型在照片上指出目标
     → 多张照片合成三维位置范围 → 规划近拍视点和航线（安全检查）→ 近拍 → 判断 → 报告
```

1. **理解检查对象**：Claude 把指令转成检查说明：要找的东西、要回答的问题
   （例如“窗户玻璃有没有破”）、它大概在房屋的哪一部分（屋顶、某层墙面、地面
   附近的附属结构）、尺寸大小、需要怎样看（俯视、正对、斜看）、是否能从外面
   看到。屋内、屋下、需要接触的任务一律拒绝。
2. **取样拍照**：在 M3 的扫描结果上，按检查对象所在的部分规划一组覆盖拍摄：
   屋顶从高处拍，墙面按楼层正对着拍，地面附近的结构从斜上方拍。目标是用尽量少
   的照片看到所有可能的位置。
3. **在照片上指出目标**：Claude 在每张照片上标出目标的框或点，并给出编号和简短
   描述。照片上可以叠加网格或刻度（与 M3 判断户界的做法相同），提高读数精度。
4. **合成三维位置**：把框内的像素沿视线投到深度点云或墙面、屋面上，得到三维
   位置；多张照片中的同一个目标合并成一个，给出位置范围和置信度。玻璃等深度
   测不准的表面，用 M3 拟合出的墙面平面代替。
5. **近拍视点和航线**：按目标所在表面的朝向和尺寸，计算拍摄方向和距离（让目标
   在照片中足够大），复用 M3 的视点搜索、A* 航线和 `check_plan`。大模型只提议
   目标，视点和航线由程序计算并经安全检查，原则与前面各阶段一致。
6. **判断和报告**：每个目标一张近拍照片，回答检查说明里的问题；报告里写明每个
   目标的位置（哪面墙、第几层）、结论和照片。看不清或无法安全拍到的写明原因。

水槽检查保留为一种“已知几何”的特例：目标由屋檐算法直接给出，不需要第 3、4 步。
目标贴近地面（台阶、平台）时需要低空飞行，依赖 M4 的避障。

- [ ] 设计文档（动手之前先讨论，同避障）
- [ ] 场景生成器加入烟囱、窗户（有的脏或破）、大门、平台、台阶，并记录真值
  （位置和状态）
- [ ] 检查说明的生成和拒绝不可行的指令
- [ ] 覆盖取样拍照
- [ ] 照片上标出目标，验证 Claude 的定位精度
- [ ] 多视角合成三维位置
- [ ] 按目标表面规划近拍视点
- [ ] 通用报告；水槽检查改成走同一套流程的特例

**完成标准**：在仿真中用几类不同的指令（例如“看看烟囱有没有裂缝”“二楼哪些窗户
破了”“后门的台阶有没有损坏”）各跑若干个场景：目标找全，位置误差在 1 米以内，
判断与真值一致；全程不违反安全限制；做不到的指令明确拒绝并说明原因。

## 9. 主要风险

| 风险 | 应对 |
|---|---|
| Mac 虚拟机跑带相机的仿真太慢 | 控制类开发留在 Mac，视觉仿真到时再评估云端 GPU 或带独立显卡的电脑 |
| 靠近房屋时 GPS 不可靠 | M4 加入视觉定位，并保持与建筑的距离 |
| 电线、细树枝等难以探测的障碍 | 飞行高度和距离留足余量，真机阶段限定在已勘察过的房屋 |
| 住宅区内与旁人的距离不满足基础证书要求 | 试飞前核对法规和空域，必要时考取高级证书或更换场地 |
| 仿真与真机差异大 | M7 中持续记录差异并回头修正仿真 |
| 隐私信息误提交到公开仓库 | 见下一节 |

## 10. 仓库与隐私约定

这是公开仓库，以下内容一律不提交：

- API 密钥和任何凭据（放在 `.env`，参考 `.env.example`）
- 真实的经纬度、航线和围栏文件
- 真机的飞行日志和参数导出
- 实拍的照片、视频和传感器录制数据
- 真实地点的地图和三维重建

计划中的目录结构：

```
wukong/
├── docs/          文档
├── src/           ROS 2 功能包
├── sim/           仿真世界和模型
├── config/        配置（真实环境的配置放 config/local/，不提交）
├── scripts/       环境搭建和启动脚本
└── private/       本地私有文件，不提交
```

引入第三方库前先确认其许可证。GPL 类许可证的库会约束与之链接的代码，需要单独评估。
